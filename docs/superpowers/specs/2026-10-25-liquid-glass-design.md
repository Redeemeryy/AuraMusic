# 灵音：Liquid Glass 改版与 OriginOS 6 适配方案

状态：待用户审阅，尚未开始产品代码修改。日期：2026-10-25。

## 1. 目标与基线

让界面接近 Apple Liquid Glass 的层次与交互原则，解决现有小屏/横屏适配问题，让设置页提供真正可操作的设置，并排查 vivo X200 Pro mini / OriginOS 6 原子岛完全不显示的问题。

代码基线 main / 24218dd / v1.1.6。保留 Kotlin + WebView、Media3 ExoPlayer、Ceru/LX 插件和现有四个主入口。本方案不引入前端框架，不改变包名，不重做音源接口。下列具体布局、默认值与实现取舍是设计建议，等待用户确认。

## 2. Apple 官方依据与视觉方向

本次实时查阅的官方材料：

- [Materials](https://developer.apple.com/design/human-interface-guidelines/materials)：Liquid Glass 用于内容上方的导航/控制层；内容层使用标准材质；regular 注重清晰度，clear 适合丰富媒体背景。
- [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)：克制使用材质、避免控件拥挤、保持滚动边缘可读性，并测试降低透明度和减少动效。

这些是当前官方公开指导，不将搜索结果推断成某个未核实系统版本的新规范。Android WebView 无法调用 Apple 的原生玻璃渲染器；目标是还原层次、通透度、边缘高光和交互反馈，不宣称像素级复制系统光学折射。

建议采用「清透中性玻璃 + 音乐封面色」：

- 底色用柔和中性浅灰，正文近黑，次级文字中灰；保留灵音蓝作为选中与主操作色。
- 内容卡片去掉普遍的磨砂、粗白描边和蓝色阴影。封面成为主要色彩来源。
- 玻璃只重点用于底部导航、迷你播放器、悬浮操作按钮与弹出面板；不把每一首歌都装进玻璃盒子。
- 玻璃呈现来自背景透色、适量模糊、细边缘高光和柔和阴影。regular 用于文字较多的导航/面板；更清透的材质只用于封面背景上的少量控制。
- 主标题约 28–32px，正文 15–16px，辅助信息 12–13px。关键触控区至少 48 CSS px；文字放大后保持操作完整。
- 普通反馈约 180–240ms，面板进入约 280–360ms。去掉整体夸张果冻缩放；按压轻微缩放且不影响布局。
- 开启减少动效时关闭唱片旋转、呼吸光晕和大位移动画；降低透明度时改为高对比的实色控制层。不支持 backdrop-filter 的 WebView 同样回退到实色。

## 3. 页面方案

### 发现

顶部显示「发现」与简洁的音源状态入口。首屏主区域是每日推荐封面卡，随后为精选歌单和榜单。封面、标题与留白构成层次，减少宣传徽章与重复状态文字。未导入音源时显示一个清楚的引导卡，提供导入按钮，不展示虚假的推荐数据。

底部放独立迷你播放器和圆角胶囊导航：两者间留出 8–12px，不在玻璃容器内再叠玻璃容器。列表可以滚至导航下方，但最后一项始终能滚动到无遮挡区域。

### 搜索与资料库

搜索框采用单一清晰输入面，不用多层高光；分类、音源选择在紧邻搜索框的位置。结果以封面、曲名、歌手、必要的音质标签呈现，取消重复卡片阴影。键盘弹出时隐藏底部导航与迷你播放器以释放空间，收起后恢复；搜索条件保持。

资料库保留收藏歌曲、收藏歌单、历史入口。统一空状态和操作尺寸。长曲名省略，详情可查看完整信息；长歌单标题最多两行。

### 播放器

保留现有唱片/歌词切换，不强行删除现有特色。减少彩色光斑，把封面颜色作为低强度背景氛围；曲名、歌手、进度、播放操作形成清楚的纵向顺序。

主要播放键突出，上一首/下一首与辅助操作有足够点击面积。歌词为内容层，当前行强调，其他行仍可辨认。横屏采用封面/唱片与歌词双栏，底部控件按空间排列，不将操作缩小至 28px。

### 歌单、评论、音源与音质面板

歌单信息和操作栏分行：主要操作「播放全部」，次要操作「收藏」「导出」，音源标签归入信息行。窄屏允许次要操作换行，避免横向挤压或必须横滑才能看到操作。

面板设置最大可用高度，标题/关闭按钮固定，内容独立滚动，底部操作保留安全区。手机使用底部面板，较宽窗口使用居中限宽面板。弹层打开时底层不可交互，关闭后恢复焦点；Android 返回键优先关闭最上层。

## 4. 设置页：每个设置对应真实行为

| 分组 | 项目 | 行为与默认值 |
| --- | --- | --- |
| 音源 | 当前插件、导入/管理/检查更新 | 复用现有功能，状态简短、操作直接 |
| 播放 | 首选音质 | 标准/高清/无损/母带；保留已有用户选择，新用户沿用母带；说明实际取决于音源且会降级 |
| 播放 | 播放模式 | 顺序/单曲循环/随机；沿用顺序默认；与播放器、队列入口双向同步并持久化 |
| 外观 | 降低透明度 | 默认关闭；打开后玻璃改为清晰实色，立即生效并持久化 |
| 外观 | 减少动效 | 默认尊重 WebView 可检测的系统偏好；用户开启后减少位移、旋转与光晕；立即生效并持久化 |
| 系统播放 | 通知与锁屏控制 | 显示系统可查询的实际权限状态，按钮打开本应用通知设置；返回后刷新 |
| 系统播放 | 原子岛帮助与诊断 | 查看通知/媒体会话/前台服务状态；说明系统显示由 OriginOS 决定；不设置没有真实效果的“强制开启”开关 |
| 数据 | 清除播放历史 | 明确命名，不再叫“清理播放缓存”；显示数量，二次确认，仅清历史，保留收藏/歌单/插件/队列 |
| 关于 | 版本与检查更新 | 从原生读取版本，复用已有 GitHub Release 更新流程，避免硬编码过期版本 |

移除「高质感已开启」「原生 MediaSession」等无操作价值的宣传行。技术诊断收进二级页面，正常用户不必阅读实现细节。

新设置独立命名保存；读取异常时回退默认值，不清空其他 localStorage 内容。音质与现有 jelly_preferred_quality 保持兼容。模式调整必须复用同一状态更新函数，避免多个入口不同步。

## 5. 响应式与适配

目前代码有 38px/24px 最低安全区、仅凭 orientation 切换车机布局、横屏 28–34px 控件、较强的 nowrap/min-width 限制。这些是代码层面已发现的问题点，视觉溢出需要逐尺寸验证。

- 使用原生 WindowInsets 作为 Android 安全区来源，网页 env 作为浏览器回退，不叠加硬编码最低状态栏高度。
- 单一布局变量管理导航高度、迷你播放器高度与内容底部空间；播放器隐藏时释放占位。
- 断点综合宽度和可用高度：小屏竖屏单列；足够宽的横屏/平板侧边导航；短窗口压缩装饰区域而非按钮。
- 使用动态视口单位并提供旧 WebView 回退；键盘占用通过实际窗口/insets 更新，不把键盘误认成车机横屏。
- 320、360、393、430px 宽度；手机横屏 800×360；平板 1024×768；文字放大 130% 进行覆盖验证。真机尺寸以设备实际读数为准。
- 全局不出现水平滚动；所有底部按钮可见可点；面板不会被键盘/导航遮住；横竖屏切换保持页面、播放和弹层状态。
- 构建时生成本地样式资源，替换运行时 Tailwind CDN；字体/图标提供离线可用方案，确保断网后导航与布局正常。引入的工具只用于构建，不引入前端应用框架。

## 6. 原子岛：现有证据、假设与排查方案

### 已确认

用户设备为 vivo X200 Pro mini，ADB 型号 V2419A，Android 16，用户报告 OriginOS 6。安装版本为 1.1.6 / code 8。

用户播放并回到桌面后，只读诊断确认：

- com.auramusic.app 进程运行；MusicService isForeground=true，前台通知 ID 1001。
- JellyAudioSession active=true、state=PLAYING，系统媒体按钮目标指向灵音。
- 通知权限 granted=true，播放通知通道 importance=4，通知含 MediaStyle 和 android.mediaSession Token。
- 通知携带现有 superx/island 相关 extras，但这不能证明厂商认可协议或实际展示胶囊。
- 用户仍报告原子岛完全不显示。没有获得 SystemUI 明确拒绝原因，不能宣布根因已定位。

Git 历史确认：v1.1.2 / 2df52d1 将 applicationId 从 com.salt.music 改为 com.auramusic.app，以消除与其他播放器的包名冲突。系统识别与包名的关联属于优先验证假设，不能恢复冒用其他应用包名作为修复。

### 厂商边界

[vivo 原子通知接入指导](https://dev.vivo.com.cn/documentCenter/doc/894) 对其原子通知接入通道要求应用上架、申请审核并由厂商开通权限。但此文不等于已证明音乐媒体会话胶囊必须走同一通道。需核实 OriginOS 6 对第三方音乐会话的实际识别机制、用户开关和包名资格，不能混淆原子通知与音乐胶囊。

### 审批设计后实施的诊断与修复顺序

1. 定向读取与灵音相关的 SystemUI/通知诊断，检查原子岛用户开关和音乐识别路径，保持原包名。
2. 对照真实媒体协议检查元数据、封面、时长、状态更新；当前会话虽已 PLAYING，但通知封面读数为空，代码还存在封面异步返回覆盖后续曲目的可能，需要独立复现。
3. 修复能复现的状态/生命周期/通知问题，再逐项验证，避免继续堆积未经证实的厂商字段。
4. 若有官方有效协议，在隔离的兼容层实现；如果为系统侧资格或开关问题，提供准确处理路径与诊断结果。
5. 验收需在当前真机上确认胶囊实际出现、点击回到播放器、暂停/恢复/切歌正确。仅通知存在或 extras 增加不算通过。

若最终确认需要厂商准入，单独说明阻塞条件；不能把普通通知恢复冒充原子岛已修复。不会替用户发送申请或变更开发者账号。

## 7. 实施边界与验证

先改共享样式/布局，再接入设置，媒体修复按复现证据单独推进。新增样式按组件组织，清理冲突旧规则，避免无止境追加 !important。保持已有插件协议和用户数据兼容。

验证包括设置持久化与双向同步、清历史边界、窄屏长文本、键盘、横竖屏、断网界面、减少动效和透明度回退。原生部分检查通知权限被拒绝、缓冲/播放/暂停/结束/报错、切歌封面竞态和后台控制。重要行为先写能失败的测试，再实现。

当前 PATH 没有 Java，但找到本机 JetBrains 附带 JBR，可在后续核对版本后用于构建；SDK 现有平台为 36/36.1，项目需要 34，Gradle 8.7 缓存尚未发现，构建准备仍需完成。

真机更新前验证现有安装包签名。签名不匹配时不卸载原应用，不丢失收藏和插件；选择可共存测试构建或等待原签名。设计审批不等于对外发布，后续交付代码、检查结果与可验证安装包，不自动上传 Release。
